# 매칭 CRUD 구현 및 검증 기록

개발 시작 기준 main: `5de929a` (2026-11-01). 확정 API A9~A13·A16, 공식 R8 DDL과 공통 MatchEntity·Repository를 사용한다. 변경 사항은 PR #77에서 검토한다.

## 구현 범위

- A9 POST `/api/matches`: 201 + JSON 숫자 matchId. 시설 내부 PK를 serviceId로 받는다. 회원 잠금 → 회원·시설 Feign 검사 → 매치·OWNER 참가 저장. 새 매치의 최소 정원은 2명이다.
- A10 GET `/api/matches`: 조건 검색과 현재 인원 일괄 집계. 기본 상태 RECRUITING·CLOSED·IN_PROGRESS. 완료·취소는 명시적 status 조건으로 조회. distance는 null. 시설·종목·성별·실력·시간·정원·지역·무료 여부·제목·설명 필터 지원. 정렬은 시작 시각, ID 오름차순이며 DB 조회에서 최대 500건만 가져온다. 응답은 기존 배열 형태다. 500건을 넘는 결과는 반환되지 않으므로 조건을 좁혀 검색해야 한다.
- A11 GET `/api/matches/{id}`: 시설 복사본과 회원 I2 프로필, OWNER·참가 여부 반환. 비로그인 플래그 false. 프로필 누락은 `알 수 없음`. 시설 서비스는 다시 호출하지 않는다.
- A12 PUT `/api/matches/{id}`: 방장만 시작 전에 수정. 정원 2명 미만 또는 현재 인원 미만 거절. 시설·종목은 기존 값 유지. 기존 시설 I3 검사 후 복사본 갱신. 정원과 현재 인원에 따라 모집 상태를 재계산하고 바뀐 경우에만 공용 Outbox에 상태 이벤트 저장.
- A13 DELETE `/api/matches/{id}`: 방장·시작 전·모집 상태에서 참가 삭제 → flush → 매치 삭제. 대기열은 R8 FK CASCADE. 삭제 이벤트는 발행하지 않는다.
- A16 GET `/api/matches/me`: Gateway 사용자 ID만 사용한다. 회원 재조회 없이 OWNER·PARTICIPANT와 과거 기록을 시작 시각 내림차순으로 반환한다.

## 기존 작업과 연결

생성·수정·삭제는 `participationMemberLocks`를 쓰며 Saga와 같은 회원 잠금 이름을 공유한다. 생성의 회원 검사와 OWNER 저장이 한 트랜잭션에서 잠금으로 보호된다. 수정·삭제는 회원 잠금 후 공통 매치 행 잠금을 얻는다. A13 삭제와 탈퇴 Saga의 데드락 재현 결과에 따라 `WithdrawalStore.lockMatches`도 매치 행을 ID 순서로 먼저 잠그고 참가 기록을 현재 읽기로 재확인한다.

생성 시 시설 검사에는 PR #47의 MatchFacilityIntegration을, 상세에는 MatchRemoteChecks.profiles를 사용한다. 생성·수정 실패는 해당 저장 트랜잭션을 롤백한다. 수정은 시설 검사를 잠금 전에 끝내고, 매치 행 잠금 후 권한·상태·기간·정원·시설 ID를 재확인한다. 상세 응답의 회원 프로필 조회는 저장 트랜잭션을 커밋한 뒤 수행한다.

DB 엔티티·DDL·권한·Compose·다른 서비스는 수정하지 않았다. 검색을 위해 MatchRepository에 JpaSpecificationExecutor를 추가하고, 입력 검증용 validation 의존성을 추가했다.

## 연결 및 후속 작업

1. 환우님과 탈퇴 Saga 담당자가 검색 의미와 `WithdrawalStore.lockMatches` 잠금 순서 변경을 검토한다.
2. A17 방장 soft cancel, A29 관리자 통계, 시작·종료 스케줄러는 이번 CRUD 범위 밖이며 후속 연결이 필요하다.
3. 시작 하루 전 알림 `match.starting-soon.v1`의 발행 및 모임당 한 번 처리도 별도 작업이다.
4. 정원 증가 시 현재 확정 명세대로 RECRUITING으로 재계산한다. 기존 대기자를 정원 수정 순간에 자동 승급시키는 추가 정책은 구현하지 않았다. 현재 #35는 참가 취소·회원 탈퇴 시 승급한다.
5. 생성 시 OWNER 자동 등록에는 joined 이벤트를 별도로 만들지 않는다. API와 CRUD 서비스의 생성·수정 최소 정원은 2명으로 바꿨다. 기존 정원 1명 기록을 읽을 수 있도록 도메인과 DB 제약은 1명 허용을 유지한다. A9 API 명세의 기존 "정원 1 이상"도 팀 계약에서 2명으로 갱신해야 한다. A10의 `maxParticipant`는 검색 상한 조건이므로 최소값 1을 유지한다.
6. H2·MockMvc 테스트와 별도로 격리된 Compose에서 MariaDB·Gateway·시설·회원 서비스 통합 호출을 검증했다. 다중 매치·여러 경합 타이밍까지 증명한 것은 아니므로 #32 완료로 판정하지 않는다.

## 테스트

MatchCrudTest에서 숫자 생성 응답, 회원 잠금 순서, 시설 스냅샷·OWNER 저장, 생성·수정 최소 정원 2명과 입력·검색 검증, 기본 상태 필터, 상세 프로필·플래그, 수정 상태 전이·권한·정원·시설 장애 롤백, terminal 상태 제한, 삭제 CASCADE, 내 매치 회원 재조회 없음, 상태 이벤트 저장 실패 시 정원 수정 롤백을 확인한다. 기존 매칭 전체 회귀 테스트와 bootJar도 실행한다.

2026-11-01 실행 결과: `:match-service:test :match-service:bootJar` 성공. 총 115건 중 103건 성공, 별도 실서비스 실행 조건이 있는 12건 제외, 실패 0건. 신규 CRUD 테스트 11건을 포함한다. 당시에는 실서비스 CRUD 통합 검증 전이었다.

2026-11-02 검토 결과: A10의 제목·설명 대소문자 무시 및 지역 부분 검색을 회귀 테스트로 확인했다. A12 시설·프로필 원격 호출이 매치 행 잠금 중 실행되지 않도록 바꾸고 트랜잭션 경계 테스트를 추가했다. `:match-service:test :match-service:bootJar` 전체 실행이 성공했다.

CodeRabbit의 A10 무제한 조회 지적을 반영해 DB에서 최대 500건을 조회하도록 제한했다. 501건의 매치를 저장한 회귀 테스트에서 응답 배열 500건과 시작 시각·ID 순서를 확인한다. A10 문서에는 결과 상한이 명시되지 않았으므로 팀 API 명세에도 이 제한을 반영해야 한다.

격리된 Compose(MariaDB 11.4)에서 Gateway 경유 A9 생성 201, A10 제목·설명·지역 검색 각 1건, A11 상세, A12 수정, A16 내 매치, A13 삭제 204를 확인했다. 실제 회원 탈퇴 API가 Kafka 이벤트를 발행하는 환경에서 A13 HTTP 삭제와 탈퇴 Saga를 병렬 실행했고, 두 번째 시도에서는 별도 DB 세션이 매치 행 잠금을 잠시 유지해 경합을 만들었다. 삭제 204, 탈퇴 접수 202, Saga CLEANED, 회원 WITHDRAWN, 최종 매치 0건을 확인했다. 기존 SQL 잠금 순서에서는 MariaDB 1213 데드락을 재현했고, 매치 행 우선 잠금으로 바꾼 뒤 같은 DB 경합에서는 재현되지 않았다. 테스트 컨테이너는 종료했으며 팀 DB는 사용하지 않았다.
